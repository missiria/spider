# Security review — Spider private beta (MISS-0095, 2026-10-15)

Scope: the code on `main` as of 2026-10-15, single-workspace invite-only beta. Re-run this
review when multi-tenant workspaces (Sprint 1) or OAuth (Sprint 2) land.

## Authentication and sessions

| Item                | State                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Credentials         | bcrypt (cost 10) password hashes; `users.password_hash` never leaves the API (`toPublic()`), login replies carry only id/email/name/role.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Login brute force   | `POST /auth/login` throttled 10 / minute / **client IP** plus a **per-account** lock (10 failures / 15 min → 429) so a distributed attacker cannot bypass the IP limit. The client IP comes from the socket, or from `x-spider-client-ip` only when the request carries the shared `INTERNAL_PROXY_SECRET`; the Next server fills it exclusively from `X-Real-IP`, which our nginx sets from `$remote_addr` on every request (client-supplied `X-Real-IP`, `CF-Connecting-IP`, `X-Spider-*` headers are overwritten/cleared at nginx) and nginx resolves the visitor behind Cloudflare with `set_real_ip_from <CF ranges>` + `real_ip_header CF-Connecting-IP` (`deploy/nginx/spider.conf`). The hard lock is keyed on (account, IP; IPv6 reduced to its /64) so an attacker cannot lock a victim out from elsewhere. An **account-wide soft limit** (> 20 failures / 15 min from any IP) adds a progressive delay (0.5–4 s) to every attempt on that account instead of locking it. Unknown accounts are tracked and answered exactly like known ones (same 401 / 429 wording, dummy bcrypt compare for equal timing), so neither the lock nor timing reveals which accounts exist. Maps are bounded; when full, unlocked entries are evicted before locked ones (MISS-0110). Failures logged with email + IP. |
| Token               | JWT HS256, `JWT_SECRET`, 24 h expiry, carries `ver` = `users.token_version`. **Every request re-reads the user** (ADR-0007): a deleted or deactivated account, a bumped `token_version` (deactivation, admin "Sign out everywhere" `POST /users/:id/revoke-sessions`, self `POST /auth/revoke-sessions`) or a changed role takes effect on the next request; role and workspace always come from the database, never from the token claims. **Production refuses to start** with a placeholder or < 32-char secret (`assertProductionConfig`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Browser session     | The Next route `/auth/session` performs the login **server-side** (credentials → API, client IP forwarded for the throttle) and stores the JWT in an **httpOnly, SameSite=Lax, Secure (https)** cookie `spider_session`; the token never reaches browser JavaScript (verified by E2E). The route rejects cross-site requests (`Sec-Fetch-Site`, `Origin`) and non-JSON bodies, so a third-party page cannot log a victim into an attacker account (login CSRF / session fixation). The API accepts the cookie via an extractor; the bearer header still works for scripts. Sign-out deletes the cookie.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| CSRF                | Cookie is SameSite=Lax and the API only accepts JSON bodies through the validation pipe; cross-site form posts cannot carry `application/json`. Revisit if any endpoint ever accepts form encoding.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Authorization       | Global `AuthGuard` (every route except `/`, `/health`, `/auth/login`); `RolesGuard` with `@Roles('admin')` on user invites / deactivation / session revocation, branding, webhook processing. Profile edits are own-only (`/auth/me`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Tenancy             | `workspace_members` (ADR-0007). The JWT strategy resolves the caller's workspace from the membership table into a per-request AsyncLocalStorage scope; every service reads it from there. Without a scope (cron) `current()` throws instead of guessing; schedulers iterate workspaces with `runAs()`. Two-tenant E2E proves a second workspace cannot list, read, mutate, assign, delete or export the first one's properties, views, opportunities, reports, webhooks, users or health.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Beta access         | Invite-only: admins create accounts in System → Beta access; the temporary password is returned once and never stored in clear. Deactivation blocks login; self-deactivation refused.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Self-service signup | `POST /auth/register` (MISS-0116) creates an **unverified** account and mails a confirmation link (24 h). Only a confirmed address (`POST /auth/verify-email`) becomes **pending** and visible to operators, so nobody can pre-claim someone else's email with their own password; re-registering an unverified address replaces it (a stranger cannot squat the owner's email; earlier links die), and **confirming requires the signup password as well as the link**, so the inbox owner can only confirm a request they made themselves. The per-address hourly mail cap is checked before the record changes. Unverified / pending accounts cannot sign in (403 with the reason, said only after the right password; rejected accounts answer like bad credentials). Spider reads GSC through one shared service account, so an unknown account must never be able to add properties on its own. Operators (admins of the default workspace) review in System → Signups (`/signups`); approval creates the person's own empty workspace. Same 202 answer for a new or existing email, bcrypt done either way, mails sent in the background: no enumeration. Throttled 5 / minute / client IP. Approval gates _who_ gets in, not _which_ properties they may add — only approve people you know.            |
| Password reset      | `POST /auth/forgot-password` always answers 202; for an active, approved account it mails `APP_PUBLIC_URL/reset-password?token=…` (32 random bytes, only sha256 stored in `password_resets`, 30 min, single use, max 3 per account per hour). Every link is **bound to the email and `token_version`** it was issued for: an email change, a password reset, a session revocation or a deactivation in between kills it. `POST /auth/reset-password` sets the password, bumps `token_version` (signs out everywhere), consumes every outstanding link of the account and clears its login lock. Both throttled per client IP; the browser calls them through the Next route `/auth/account/*`, which forwards the trusted client IP like `/auth/session` (the `/api` rewrite would make every visitor share one IP). Requires SMTP (`SMTP_*`): without it, reset mails are skipped.                                                                                                                                                                                                                                                                                                                                                                                                                             |

## Input validation and data access

- `ValidationPipe` with `whitelist` + `forbidNonWhitelisted` + `transform`: unknown body fields → 400.
- All SQL through TypeORM parameters; the only user-supplied patterns (regex filters) are
  bound parameters to MySQL `REGEXP`, length-capped at 200, syntax-checked, and MySQL's
  `regexp_time_limit` (32 ms default) bounds evaluation. Invalid patterns → 400, never 500.
- Site URLs are normalised and validated (`normalizeSiteUrl`); nothing from the user is
  interpolated into Google API calls except the validated `siteUrl`.
- Saved-view configs are stored as opaque JSON, rejected (400) above 16,000 UTF-8 bytes before
  persistence (never truncated), and parsed defensively on read.
- Dates are strict: malformed or impossible calendar dates, inverted ranges and ranges over 487
  days are 400 (no silent fallback, no 500).
- Every read/write is scoped to the caller's workspace; object lookups by id return 404
  outside it, references to another tenant's property / user are 404 / 400.

## Transport and headers

- API: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy:
no-referrer`, `Permissions-Policy`, `Cache-Control: no-store`, `x-powered-by` removed,
  `trust proxy` for correct client IPs behind nginx/Cloudflare.
- Web: same family of headers plus HSTS (1 year) from `next.config.ts`; `poweredByHeader` off.
- CORS: `CORS_ORIGINS` allow-list with credentials; production start refuses an empty list.
- TLS terminates at Cloudflare (proxied DNS); nginx serves HTTP on the VPS loopback only
  (`deploy/nginx/spider.conf`). Use Cloudflare "Full (strict)" + certbot if the origin must
  also be encrypted.

## Google Search Console access

- One service account (ADR-0002), **read-only** scope `webmasters.readonly`; key arrives as
  `GSC_SERVICE_ACCOUNT_JSON` (base64) in `deploy/env/api.env`, gitignored. It is never
  returned by any endpoint (only `client_email` is).
- Rate limits respected by pacing (`GSC_PACE_MS`) and backoff; quotas documented in ADR-0004.
- Revoked access is detected by the checker and shown as "Access revoked"; data is retained
  until the property is deleted (documented in the onboarding screen).

## Outbound integrations (MISS-0094)

- Webhook payloads are signed (`X-Spider-Signature: t=…,v1=HMAC-SHA256(secret, t.body)`, secret
  shown once at creation, never returned again); receivers reject stale `t` (> 5 min) and bad
  HMACs — reference verifiers in `docs/WEBHOOKS.md`. Payloads carry only the workspace's own
  data; a webhook is scoped to its workspace.
- Webhook URLs: https only in production, no credentials in the URL; the hostname is **resolved
  with DNS at creation and again at every delivery**, every returned address must be public —
  addresses are parsed to bytes; IPv4 private/loopback/link-local/CGNAT/test/reserved, and IPv6
  loopback, ULA, link-local, site-local, multicast, documentation, Teredo, plus every
  IPv4-embedding form (mapped `::ffff:`, SIIT, compat `::/96`, NAT64 `64:ff9b::/96` and
  `64:ff9b:1::/48`, 6to4 `2002::/16`) are classified by the embedded address; anything outside
  global unicast `2000::/3` is refused and the validated address is **pinned** for the connection (undici Agent with a
  fixed lookup, SNI kept on the hostname) so DNS rebinding cannot redirect the request;
  10 s timeout, redirects not followed, 4 attempts with backoff, admin-only management.
- SMTP: certificate verification is **on by default** (`SMTP_REJECT_UNAUTHORIZED=true`); set
  `false` only for a local relay with a self-signed certificate.
- Report emails go through the configured SMTP relay; recipients are validated and capped at 20
  per schedule; attachments are generated server-side from the stored data only.
- CSV exports neutralise spreadsheet formula injection (`=`, `+`, `-`, `@` prefixes).

## Audit and observability

- `opportunity_events` is append-only for every status/priority/assignee/due/note change.
- Sync runs keep `sync_runs` rows with per-dimension details and errors; failures surface on
  the property (`last_error`), on the System page and in `GET /settings/health` (used by
  `scripts/smoke.sh`).
- Login success/failure lines in the API log (pm2) with user id / email and IP.

## Known gaps (accepted for the private beta, tracked)

1. One workspace per user and no self-service workspace creation or switching: an operator
   creates a customer workspace (`WorkspacesService.create`) and its first admin; the admin then
   invites inside it. Google OAuth (MISS-0090) is not implemented: all workspaces read GSC
   through the one service account, so a customer must share their properties with it.
2. No password reset / change flow: admins re-invite (new temporary password) if needed.
3. No Content-Security-Policy header yet (Next inline theme script needs a nonce strategy).
4. No MFA.
5. Rate limiting and the per-account lock live in API process memory (no shared store); fine for one PM2 instance.
6. Backups rely on the VPS `mysqldump` cron described in `deploy/PRODUCTION.md`; no offsite copy
   is configured by this repo.

No critical or high finding remains open against the beta scope.
